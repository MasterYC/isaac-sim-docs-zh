多刻度渲染#

Tool Reference

多刻度渲染将每个传感器的渲染频率与主仿真帧率解耦。 系统不再每帧渲染所有传感器，而是让每个传感器以各自可配置的频率独立运行。 通过避免冗余的渲染工作，这显著提升了包含大量传感器的场景的性能。

在 Isaac Sim 6.0 及更高版本中，多刻度渲染默认启用。

概述#

在 Isaac Sim-6.0 之前，每个摄像头和 RTX 传感器均以仿真帧率进行渲染。启用多刻度渲染后，渲染器会为每个传感器维护独立的刻度计数器，并且仅当传感器的刻度间隔到期时才渲染该传感器。

每个传感器 prim 上的 omni:sensor:tickRate 属性以 Hz 为单位控制渲染频率。值为 0（默认值）时，传感器将处于自动触发模式，即每帧都进行渲染，就像禁用了多刻度渲染一样。

性能优势#

  • 降低 GPU 负载：无需每帧更新的传感器将完全跳过渲染，从而释放 GPU 资源供其他传感器或仿真任务使用。

  • 独立速率：以 60 Hz 运行的立体深度摄像头不再强制 30 Hz 的 RGB 摄像头以相同速率渲染。

  • 更好的扩展性：包含大量传感器的场景（例如多机器人车队）将获得成比例更大的性能提升，因为每个传感器仅在实际触发刻度时消耗 GPU 时间。

配置每个传感器的刻度速率#

传感器刻度速率由 OmniSensorAPI USD 架构中的 omni::sensor::tickRate 属性控制，该架构应用于 Camera 和 OmniLidar prim。Isaac Sim 6.0 中随附的 USD 资产已应用此架构，并设置了适当的默认刻度速率。

注意

OmniSensorAPI schema 也应用于 OmniRadar prim，但在 Isaac Sim 6.0 GA 中，RTX Radar 渲染器会忽略 omni:sensor:tickRate 并始终自动触发。请参阅 6.0 GA 中的 RTX Radar 自动触发。

使用 Isaac Sim 扩展 API#

isaacsim.sensors.experimental.rtx 扩展提供了用于创建传感器 prim 并配置其 tick 速率的 Python API。 例如，要在 /World/Lidar 处创建一个 tick 速率为 10 Hz 的 OmniLidar prim：

from isaacsim.sensors.experimental.rtx import Lidar

# Render the Lidar at 10 Hz independently of the simulation frame rate.
lidar = Lidar(path="/World/Lidar", tick_rate=10.0)

对于相机：

from isaacsim.sensors.experimental.rtx import RtxCamera

# Render the Camera at 30 Hz independently of the simulation frame rate.
camera = RtxCamera(path="/World/Camera", tick_rate=30.0)

使用 OmniGraph#

使用 ROS2、UCX 或 HSB 辅助 OmniGraph 节点时，传感器 tick 速率从传感器 prim 上的 omni:sensor:tickRate 属性读取。 无需额外的节点配置。

有关根据仿真帧率缩放传感器和图形发布速率的完整 ROS2 示例，请参阅 ROS 2 设置发布速率。

OmniLidar Tick 速率必须等于 scanRateBaseHz#

警告

对于 OmniLidar prim，omni:sensor:tickRate 必须设置为等于 omni:sensor:Core:scanRateBaseHz，以确保扫描累积和多 tick 渲染正确运行。

如果这两个值不同，Lidar 模型将回退为每帧生成部分扫描，而不是累积成完整旋转（旋转式 Lidar）或完整方位角扫描（固态 Lidar）。假设每个 tick 生成完整扫描的下游流水线——包括 ROS2 RTX Lidar Helper laser_scan 发布者、IsaacComputeRTXLidarFlatScan 以及任何使用累积 GenericModelOutput 数据的消费者——会静默地看到截断的输出。在这种情况下，渲染器不会记录错误。

例如，随附的 Example_Rotary Lidar 配置具有 scanRateBaseHz = 10，因此传感器必须以 10 Hz 的频率进行 tick：

from isaacsim.sensors.experimental.rtx import Lidar

# Render at 10 Hz regardless of simulation frame rate.
lidar = Lidar.create("/World/Lidar", config="Example_Rotary", tick_rate=10.0)

同样的约束也适用于 Example_Solid_State 以及 RTX Lidar Sensors 中的厂商配置。在包装现有的 OmniLidar prim 时，请从该 prim 读取 omni:sensor:Core:scanRateBaseHz，并将该值作为 tick_rate 传入。

架构：时间线、物理和渲染器#

启用多 tick 渲染后，三个时钟在每个 omni.kit.app 更新期间独立推进。本节将解释每个时钟是什么、每个时钟如何推进，以及它们如何交互。在某些配置中，混合 omni.timeline 时间与物理或传感器时间的代码可能会产生不一致的时间戳，因此在配置确定性仿真或解释传感器输出时，这些关系至关重要。

每帧顺序#

对于播放中的单个 App.update()：

  1. 运行循环计算 loop_dt（手动或挂钟），并且 omni.timeline 按 loop_dt 推进。

  2. 物理阶段更新阶段运行 N >= 0 个 physics_dt 子步骤以追赶 循环时间。每个子步骤重新计算物理模拟时间并将其写入 /ExternalSimulationTime。

  3. Hydra 读取 /ExternalSimulationTime 一次。每传感器 tick 调度器将该值与 每个传感器的最后渲染时间及其 omni:sensor:tickRate 进行比较，以 决定哪些传感器在此帧渲染。

  4. IsaacReadSimulationTime 等 OmniGraph 节点读取相同的模拟时间， 要么直接读取，要么在给定参考帧 RationalTime 时，通过 isaacsim.core.simulation_manager 维护的 TimeSampleStorage 环形缓冲区进行插值。

在 physics_dt <= loop_dt 的情况下，同一帧内的多个物理子步都会写入 /ExternalSimulationTime，但渲染器只读取最后一个值。TimeSampleStorage 将这些写入操作合并为每帧一个样本，以该帧的 RationalTime 为键，保存累积的物理时间。

在 physics_dt > loop_dt 的情况下，未执行物理步的帧会使 /ExternalSimulationTime 保持不变。渲染管线仍会在每次应用更新时运行，但每个传感器的计时计数器不会推进，且在这些帧上没有任何传感器产生新的输出。当物理最终步进时，prim 会向前跳跃 physics_dt，并且到期的传感器会在该帧进行渲染。

当 useFixedTimeStepping=true 时（完整的 Isaac Sim GUI 默认设置）#

上面的表格描述了当 /app/player/useFixedTimeStepping 为 false（独立 Python 中的默认值）时适用的子步追赶行为。 完整的 Isaac Sim GUI 应用在 source/apps/isaacsim.exp.full.kit 中将该 carb 设置设为 true。 当该设置为 true 时，时间轴会忽略运行循环测得的 dt，并在 Timeline::update() 内每次接受的更新中强制使用 dt = 1 / timeCodesPerSecond。 随后，传感器和时间轴时间按以下速率推进：

sim_advance_per_wall_sec  =  (1 / timeCodesPerSecond)  *  loop_hz_wall

后果：

  • 如果 loop_hz_wall == timeCodesPerSecond（两者默认均为 60 Hz），则 sim/wall = 1.0，系统以实时运行。 这是单独调用 isaacsim.core.rendering_manager.RenderingManager.set_dt() 时配置的行为——它将 rateLimitFrequency、targetFramerate 和 timeCodesPerSecond 对齐到相同的值。

  • 如果 loop_hz_wall < timeCodesPerSecond（例如，循环速率限制低于时间轴的每刻度速率），则模拟以比率 loop_hz_wall / timeCodesPerSecond 以慢动作运行。 由 /ExternalSimulationTime 门控的 RTX 传感器发布频率按比例降低；由 OnPlaybackTick 驱动的发布者（/clock、OmniGraph 刻度）仍以 loop_hz_wall 触发。 这是用户仅设置 /app/runLoops/main/rateLimitFrequency 而未更新 timeCodesPerSecond 时遇到的陷阱：物理步长时间和挂钟时间以不明显的方式解耦。

  • 如果 loop_hz_wall > timeCodesPerSecond，行为取决于 /app/player/useFastMode（也作为 timeline.set_play_every_frame(...) 暴露）：

    • ``useFastMode = false``（默认值）：时间轴进行子采样（在每第 N 个运行循环 tick 时推进时间，其中 N = ceil(targetFramerate / timeCodesPerSecond)），因此当运行循环 tick 速度更快时，时间轴仍保持其配置的速率。这用于驱动更高的渲染产品 / OnPlaybackTick 速率，而不会加速模拟时间。

    • ``useFastMode = true``（例如，当调用 timeline.set_play_every_frame(True) 时设置 - 某些 Replicator 示例和基准测试会这样做）：绕过子采样门控。每个运行循环 tick 都会使时间轴推进 1 / timeCodesPerSecond， 因此模拟时间以比率 loop_hz_wall / timeCodesPerSecond 快于墙钟时间（快进）运行。这是离线数据生成的预期行为，在此场景下你希望每墙钟秒尽可能多地摄入模拟时间，但这会破坏任何假设模拟时间跟踪墙钟时间的代码。

参考示例 设置模拟速率 使用 isaacsim.core.simulation_manager.SimulationManager.setup_simulation() 加上 isaacsim.core.rendering_manager.RenderingManager.set_dt() 以保持所有三个 时钟一致 - 从构造上避免了上述所有模式。它保留 useFastMode 为其默认值 false。

实际影响#

  • 始终通过 SimulationManager.get_simulation_time()、 IsaacReadSimulationTime 或每帧 getSimulationTimeAtTime(rtime) 查找来读取模拟时间。这些返回渲染器也看到的物理驱动值，因此传感器 时间戳、TF 时间戳和下游消费者保持一致。

  • 不要使用 omni.timeline 当前时间作为传感器或消息的时间戳。 在 physics_dt > loop_dt 配置中，两个时钟每帧都会漂移，仅在物理步长时重新同步，从而产生不一致的时间戳。

  • 要使物理、渲染器和下游流水线都每帧推进一次，请通过 SimulationManager.setup_simulation(dt=1.0 / hz) 和 RenderingManager.set_dt(1.0 / hz) 设置 physics_dt == loop_dt。 isaacsim.exp.base.zero_delay.kit 体验配置了此设置，是确定性单帧 TF / 图像配对的参考设置。

从先前版本迁移#

如果您从默认未启用多刻子渲染的版本升级，以下更改 可能会影响您的工作流程。

一般更改#

  1. 更新 Camera 和 OmniSensor prim 以支持多刻子渲染。 将 OmniSensorAPI schema 应用于 Camera prim。该 schema 已默认 应用于 OmniLidar/OmniRadar prim。设置 omni:sensor:tickRate 属性以控制渲染频率。当传感器使用默认的 omni:sensor:tickRate 0（自动触发）时，多刻子渲染是透明的， 这会渲染每一帧。

  2. USD 资产已更新。随附的传感器资产现已应用 OmniSensorAPI schema。如果您拥有包含 Camera 或 OmniLidar/OmniRadar prim 的自定义 USD 资产，请应用 OmniSensorAPI schema 并设置 omni:sensor:tickRate 以控制渲染频率。

  3. frameSkipCount 已弃用。请将 ROS2/UCX/HSB 辅助节点上 frameSkipCount 的用法替换为传感器 prim 上的 omni:sensor:tickRate。请参阅下方的 frameSkipCount 弃用。

  4. RTX Lidar 累积已移至 USD 属性。Lidar 扫描累积现在由 OmniLidar prim 上的 omni:sensor:Core:accumulateOutputs 属性控制。已弃用的 isaacsim.sensors.rtx 扩展的 IsaacExtractRTXSensorPointCloudNoAccumulator 注释器及其 IsaacCreateRTXLidarScanBuffer 和 IsaacComputeRTXLidarFlatScan 节点已更新以读取此属性。较新的 IsaacExtractRTXSensorPointCloud 注释器和 OmniGraph 节点位于 isaacsim.sensors.rtx.nodes 中，并假定 GMO 缓冲区已根据 accumulateOutputs 包含完整扫描或每帧部分扫描。

  5. 将单个渲染产品等待替换为完整应用更新。omni.syntheticdata.sensors.next_render_simulation_async 辅助函数（以及任何其他针对单个渲染产品的辅助函数）在多刻子渲染下无法正确推进每个传感器的刻子计数器。请改用 isaacsim.core.experimental.utils.app.update_app_async，它执行完整的应用更新步骤，并确保处理所有传感器刻子。

    之前：

    import omni.syntheticdata

# Example values for an attached render product and a per-product wait count.
render_product_path = "/Render/RenderProduct_Replicator"
N = 1

# Deprecated: does not advance per-sensor tick counters under multi-tick rendering.
await omni.syntheticdata.sensors.next_render_simulation_async([render_product_path], N)

    之后：

    import isaacsim.core.experimental.utils.app as app_utils

# Number of full application update steps to perform.
N = 1

await app_utils.update_app_async(steps=N)

frameSkipCount 弃用#

在之前的版本中，ROS2 和 UCX 辅助节点的发布频率由每个辅助节点上的 frameSkipCount 输入控制。此参数现已弃用。

启用全局多刻度渲染后，控制传感器发布数据频率的正确方法是在传感器 prim 本身上设置 omni:sensor:tickRate。这种方式更高效，因为传感器在跳过的刻度期间完全不会进行渲染，而不是渲染后丢弃输出。

frameSkipCount 参数仍可用于向后兼容，但当使用非零值时会记录弃用警告。该参数将在未来的版本中移除。

此弃用适用于之前公开 frameSkipCount 的每个辅助节点：

  • ROS2 Camera Helper (isaacsim.ros2.bridge.ROS2CameraHelper)

  • ROS2 Camera Info Helper (isaacsim.ros2.bridge.ROS2CameraInfoHelper)

  • ROS2 RTX Lidar Helper (isaacsim.ros2.bridge.ROS2RtxLidarHelper)

  • UCX Camera Helper (isaacsim.ucx.bridge.UCXCameraHelper)

较新的 ROS2 RTX Radar Helper (isaacsim.ros2.bridge.ROS2RtxRadarHelper) 是在此弃用之后引入的，并且完全不公开 frameSkipCount。

已知问题#

6.0 GA 中的 RTX Radar 自动触发#

在 Isaac Sim 6.0 GA 中，RTX Radar 渲染器会忽略 omni:sensor:tickRate 在 OmniRadar prim 上的设置，并渲染每个仿真帧。在 isaacsim.sensors.experimental.rtx.Radar 上设置 tick_rate 对实际 渲染节奏没有影响；该属性仍会写入 prim，但多 tick 调度器会跳过 Radar prim。预计将在未来版本中修复此问题。

自动触发限制不会影响 OmniLidar 或 Camera prim。

OmniLidar 部分扫描回退#

如果 OmniLidar prim 上的 omni:sensor:tickRate 不等于 omni:sensor:Core:scanRateBaseHz，则传感器会回退为每帧发出部分扫描。有关详细信息和 建议的补救措施，请参阅 OmniLidar Tick Rate 必须等于 scanRateBaseHz。
