构建自定义 IPC OmniGraph 节点#

Tool Reference

本指南介绍如何在 Isaac Sim 中构建用于进程间通信 (IPC) 的 OmniGraph 节点。内容涵盖节点架构、使用 BaseResetNode 的传输生命周期、在 compute 中进行非阻塞 I/O，以及如何将你的传输库添加为依赖项。无论你使用哪种 IPC 技术栈，这些 OmniGraph 模式均适用。工作示例是 isaacsim.examples.ipc，这是一对基于 C++ 和 Python 的 BSD 套接字的时钟发送和步骤接收节点。教程首先使用 CLI 模板搭建一个新的扩展，以便在编写任何 IPC 代码之前拥有一个可用的构建骨架。

注意

此工作流需要 源代码检出 的 Isaac Sim 仓库。不支持使用 pip 包或二进制发行版。请在开始之前克隆 GitHub 仓库。

注意

本教程中的所有命令均在 Isaac Sim 仓库根目录（包含 build.sh/build.bat 和 repo.sh/repo.bat 的目录）中运行。

开始之前#

先决条件：

  • 自定义 C++ 扩展 — Kit C++ Extension Template。

  • OmniGraph — OmniGraph 核心概念 和 OmniGraph 基础教程。

  • 自定义节点 — 自定义 Python 节点 和 自定义 C++ 节点。

可选：Isaac Sim OmniGraph 教程，如果您不熟悉 Action Graph 编辑器。

另请参阅

ROS 2 Python 自定义 OmniGraph 节点 提供了一个完整的 Python 节点示例。虽然涉及 ROS 2 上下文，但 internal_state() 工厂、BaseResetNode、db.per_instance_state 和 og.ExecutionAttributeState.ENABLED 模式对于任何 IPC 节点都是相同的。

搭建扩展脚手架#

在编写 IPC 代码之前，请使用 CLI 模板创建扩展骨架：

./repo.sh template new

.\repo.bat template new

当出现提示时，选择 Isaac Sim OmniGraph Node Extension。系统将要求您提供以下信息：

  • extension_name 点分标识符，例如 isaacsim.my.ipc.nodes。

  • title 在 Extensions 窗口中显示的可读名称。

  • description 简短摘要。

  • category 用于在 Action Graph 节点库中对您的节点进行分组（例如 Simulation）。

模板会在 source/extensions/<extension_name>/ 下创建完整的扩展骨架：

source/extensions/<extension_name>/
├── config/extension.toml          ← metadata, dependencies, test entries
├── nodes/
│   ├── OgnExampleCpp.ogn          ← rename/replace with your IPC node schema
│   └── OgnExampleCpp.cpp          ← rename/replace with your IPC node implementation
├── plugins/<extension_name>/
│   └── PluginInterface.cpp        ← Carbonite plugin + OGN registration (keep as-is)
├── bindings/<extension_name>/
│   └── Bindings.cpp               ← pybind11 bindings; acquires the Carbonite interface (keep as-is)
├── include/<extension_name>/
│   └── IExampleNodes.hpp            ← Carbonite interface (keep as-is)
├── python/nodes/
│   ├── OgnExamplePython.ogn       ← rename/replace with your Python node schema
│   └── OgnExamplePython.py        ← rename/replace with your Python Node Implementation
├── python/impl/extension.py       ← calls acquire_example_ipc_interface() on startup to load the plugin
├── python/tests/                  ← test modules go here
└── premake5.lua                   ← build configuration

在扩展加载到 Isaac Sim 之前，必须执行构建步骤——它会编译 C++ 插件并生成用于注册节点的 OmniGraph 数据库文件。现在运行它：

./build.sh

.\build.bat

生成的节点 —— Example C++ Node (OgnExampleCpp) 和 Example Python Node (OgnExamplePython) —— 是用于将输入值加倍的占位存根。Action Graph 库中的显示名称来自每个 .ogn 文件中的 uiName 字段，而不是文件名。在后续章节中，请用您实际的 IPC 节点替换或重命名它们。

试一试：验证您的脚手架

上述构建完成后，请确认脚手架已注册其占位节点：

  1. 启动仓库构建的 Isaac Sim —— 而非单独安装的 Isaac Sim：

    ./_build/linux-x86_64/release/isaac-sim.sh

    .\_build\windows-x86_64\release\isaac-sim.bat

  2. 打开 Window → Extensions，搜索您的扩展名称（例如 isaacsim.my.ipc.nodes），然后启用它。

  3. 打开 Window → Graph Editors → Action Graph，并在节点库中搜索 Example C++ Node 和 Example Python Node。这些名称与脚手架 .ogn 文件中的 uiName 字段相匹配。

如果两个节点都显示出来，则说明脚手架已正确连接。请继续执行设计和实现您的节点以替换占位符。

如果节点未显示，请检查以下内容：

  • 构建（Linux 上的 ./build.sh，Windows 上的 .\build.bat）已顺利完成且无错误。只有在编译 C++ 插件并由构建生成 OmniGraph 数据库文件后，节点才会被注册。

  • 您启动的是仓库构建的 Isaac Sim（./_build/linux-x86_64/release/isaac-sim.sh 或 .\_build\windows-x86_64\release\isaac-sim.bat）。单独安装的 Isaac Sim 不会搜索仓库的 exts/ 目录，因此无法找到您的扩展。

  • 该扩展在 Window → Extensions 中已启用（绿色开关）。如果在构建运行之前它已启用，请先禁用再重新启用。

  • 在任何 .ogn schema 或代码更改后，必须重新运行构建并重启 Isaac Sim，更新后的节点才会显示。

添加您的传输库#

在编写节点代码之前，请接入提供 IPC 和序列化功能的库。生成的 config/extension.toml 和 premake5.lua 已就位。以下各节展示了添加条目的位置。

Python#

Isaac Sim 附带了一个 pip 归档文件（omni.isaac.core_archive 及相关扩展），其中预捆绑了许多常用包，包括 NumPy 和 SciPy。如果您的库已包含在该归档文件中，则可以直接导入，无需额外配置。

如果该包尚未捆绑，请在 config/extension.toml 中声明它，例如：

[python.pipapi]
requirements = ["pyzmq>=25", "grpcio"]  # replace with your actual packages
use_online_index = true

Isaac Sim 会在扩展启动时解析这些依赖项。必须设置 use_online_index = true。如果省略该设置或将其设置为 false，omni.kit.pipapi 会记录警告并完全跳过 requirements 列表。

C++#

预构建的原生库通过 packman 获取。这些步骤遵循 Kit Extension C++ 模板文档中描述的相同模式：

  1. 声明依赖项。 将您的库添加到 deps/ext-deps.packman.xml。该文件是用于指定扩展特定依赖项的指定文件（与 Kit SDK 依赖项分开）。解包后的目录树通常位于 _build/target-deps/<libname>/ 下：

    <project toolsVersion="5.0">
  <dependency name="mylib" linkPath="../_build/target-deps/mylib">
    <package name="mylib" version="1.2.3" />
  </dependency>
</project>

  2. 更新 ``premake5.lua``。 指向包含目录和库目录，并添加链接：

    includedirs { "%{target_deps}/mylib/include" }
libdirs     { "%{target_deps}/mylib/lib/%{platform}" }
links       { "mylib" }

  3. 运行时的共享库。 如果库以 .so / .dll 形式发布，请将其与扩展插件捆绑在一起，或在 extension.toml 的 [native.library] 下列出，以便 Kit 的加载器找到它。

示例扩展仅使用标准 BSD socket API，除插件本身外没有额外的原生库条目。

设计和实现您的节点#

设计原则#

保持 IPC 节点轻量。它们应仅处理序列化和传输。仿真数据读取（关节位置、传感器数据、仿真时间）属于上游内置节点，这些节点应在您的 IPC 节点之前接入图中。下游处理或命令写入属于其后的其他节点。这使 compute 保持快速，并使图布局具有自文档性。

每个 IPC 节点所需的内容#

无论使用何种传输方式，每个自定义 IPC 节点都需要相同的六项内容：

  • 节点架构（.ogn 文件）— 声明输入（URI、配置）、输出（数据、execOut）和状态。请参考 isaacsim.examples.ipc 中 nodes/ 下的示例 .ogn 文件。

  • BaseResetNode 子类 — 持有每个实例的状态（套接字、缓冲区、句柄）。实现 reset()（C++）或 custom_reset()（Python），以便在时间线停止或输入更改时拆除传输。

  • compute(db) 具有生命周期拆分：

    • 检测输入变化（URI、配置）→ 调用 reset 和 teardown

    • 如果未就绪，尝试打开传输 → 失败时提前返回（在下次评估时重试）

    • 执行非阻塞 I/O（发送或尝试接收）

    • 写入 db.outputs 并触发 execOut

  • 非阻塞 I/O — 切勿在 compute 中无限期阻塞。使用 try-receive、超时机制，或将慢速路径卸载到工作线程（请参阅 Performance Considerations）。

  • 触发 execOut 在 compute 结束时，以向下游节点发出信号，表明传输操作已完成和/或新数据已就绪。你可以控制触发时机。例如，可以在每次评估时触发，仅在发送成功时触发，或仅在接收到完整消息时触发。

  • 你的传输库 — 将其添加为依赖项（请参阅上文 Add Your Transport Library），并用你的技术栈 API 替换 TCP 辅助函数。

OGN Schema 快速参考#

每个 .ogn 文件都是一个单一的 JSON 对象，以节点注册的类型名称作为键。Python IPC 节点的最小 schema 如下所示：

{
    "MyNodeName": {
        "version": 1,
        "language": "Python",
        "description": "One-line description shown in the node library.",
        "metadata": { "uiName": "My Node Display Name" },
        "categoryDefinitions": "config/CategoryDefinition.json",
        "categories": "myCategory",
        "inputs": {
            "execIn":  { "type": "execution", "description": "Trigger." },
            "uri":     { "type": "string",    "description": "...", "default": "tcp://127.0.0.1:5550" },
            "myValue": { "type": "double",    "description": "...", "default": 0.0 }
        },
        "outputs": {
            "execOut":  { "type": "execution", "description": "Output execution port." },
            "myTokens": { "type": "token[]",   "description": "Array of token outputs." }
        }
    }
}

常见标量类型："string"、"double"、"float"、"int"、 "uint"、"bool"、"execution"。数组变体追加 []： "double[]"、"float[]"、"token[]" 等。对于非执行标量输入，"default" 键是 必需的；对于数组输入，使用 []。

categoryDefinitions 是相对于 nodes/ 目录的路径，指向一个 JSON 文件，该文件将类别键映射为人类可读的显示字符串：

{
    "categoryDefinitions": {
        "myCategory": "My node group label in the Action Graph library"
    }
}

BaseResetNode 在 isaacsim.core.includes 中声明。此扩展仅作为编译时依赖项，请不要将其添加到 extension.toml 中的 [dependencies]。相反，请在 premake5.lua 中添加头文件路径：

Python 节点实现#

BaseResetNode 由 isaacsim.core.nodes 扩展提供。请在 config/extension.toml 中将其添加为依赖项，并在你的节点文件中导入它：

[dependencies]

import omni.graph.core as og
from isaacsim.core.nodes import BaseResetNode

将每个实例的数据放在一个继承自 BaseResetNode 的小型类中。如果你在 compute 中延迟打开套接字（如示例所示），请将 initialize=False 传递给 super().__init__。如果不这样做，BaseResetNode.__init__ 会在构造期间立即调用 custom_reset()，此时你的实例属性（例如 self.sock = None）尚未设置，从而引发 AttributeError。实现 custom_reset() 以关闭套接字并清除缓冲区。custom_reset() 在时间轴停止时运行，并镜像 C++ 的 reset()。

将生成的 OgnExamplePython 存根替换为如下所示的类（有关完整的 TCP 实现，请参阅 isaacsim.examples.ipc 中的 OgnSimpleSendSimulationClockPy.py）：

import omni.graph.core as og
from isaacsim.core.nodes import BaseResetNode


class OgnMyIpcNodePyState(BaseResetNode):
    """Per-instance state for the template IPC node."""

    def __init__(self) -> None:
        # Declare all attributes BEFORE calling super().__init__,
        # because BaseResetNode.__init__ calls custom_reset() immediately.
        self.handle = None  # replace with your transport handle
        self.uri = ""
        super().__init__(initialize=False)

    def custom_reset(self) -> None:
        """Reset transport state when timeline or inputs change."""
        # Called on timeline stop and when inputs change.
        if self.handle is not None:
            self.handle.close()
            self.handle = None
        self.uri = ""


class OgnMyIpcNodePy:
    """Template OmniGraph node for custom IPC transports."""

    @staticmethod
    def internal_state() -> OgnMyIpcNodePyState:
        """Create per-instance state for the node.

        Returns:
            Per-instance node state.
        """
        return OgnMyIpcNodePyState()

    @staticmethod
    def compute(db: object) -> bool:
        """Evaluate one non-blocking IPC transfer step.

        Args:
            db: OmniGraph database object for the current node evaluation.

        Returns:
            True if the transfer completed successfully, otherwise False.
        """
        state = db.per_instance_state

        uri = db.inputs.uri
        if state.handle is not None and state.uri != uri:
            state.custom_reset()

        if state.handle is None:
            # Open transport from inputs (e.g. URI, config).
            # state.handle = open_my_transport(uri)
            # state.uri = uri
            # Fire execOut even on failure so downstream nodes keep running.
            db.outputs.execOut = og.ExecutionAttributeState.ENABLED
            return False

        # Non-blocking send or try-receive; write db.outputs on success.
        # See Performance Considerations for time-budget guidance.
        success = False  # replace with actual transfer

        # For send nodes: fire execOut every tick.
        # For receive nodes: fire execOut only when a full message arrives.
        if success:
            db.outputs.execOut = og.ExecutionAttributeState.ENABLED
        return success

性能注意事项#

保持在您的帧预算范围内。

OmniGraph 在那些必须相对于仿真、UI 和其他图保持响应能力的路径上评估 compute。常见的失败模式是执行时间不可预测地过长，这本身并不是“同步” I/O 造成的。等待慢速对端、进行大量数据拷贝、争用锁，或执行可能停滞数毫秒的 RPC，都可能导致性能问题。

小型、快速的路径通常没问题。

在 compute 中，一个微小、固定大小、发后即忘的操作（教程中在套接字连接后发送一次 8 字节时钟信号），如果它在目标帧率下始终能在每节点预算内完成，则可以保留在图线程上。对于其他技术栈，如果你已经测量过该路径，并且它不会等待来自远程端的背压，同样适用此规则。

何时使用工作线程、队列或异步 API。

  • 如果调用可能会阻塞未知时长（请求/响应、就绪等待、大负载，或任何可能超出每节点预算的操作），请在 worker 线程上运行该 IPC。使用将结果入队的回调，并让 compute 仅执行非阻塞出队和写入 db.outputs。

  • 对于入站数据，尝试接收（如教程中的 step 节点）可避免在外部进程未按你的计划发送时无限期等待。

  • 异步或基于回调的 I/O：在 worker 线程上驱动网络或 IPC，将解码后的消息推送到线程安全队列，并让 compute 仅执行出队（非阻塞）和写入 db.outputs。

  • 延迟完成：从 compute 提交工作而不等待回复。后台线程将结果入队，供后续评估使用。

结构化消息与固定字节。

教程中的固定大小帧格式是为了清晰起见。生产环境的桥接通常使用你的库的消息格式（IDL 生成的类型、JSON 或其他模式）。你仍然需要决定何时发送、如何解析传入数据，以及如何使每个 compute 保持在预算范围内。

大型消息（相机帧、点云）。

移动多兆字节有效载荷的单次调用可能会给内存和调度带来压力。使用流式 API、显式背压（在慢速消费者上丢弃或跳过帧），或在 OmniGraph 之外使用共享内存和零拷贝路径，节点仅传递句柄或小型元数据。

对于与外部应用程序（主题、服务或其他运行时）进行 IPC 通信，请使用专用的桥接扩展，而不是将上表中的节点视为传输层。示例包括 isaacsim.ros2.nodes（ROS 2）或 isaacsim.ucx.nodes（UCX）。这些扩展的作用与 TCP 教程节点相同，而不是表中的传感器读取节点。

本仓库中的参考实现。

source/extensions/ 目录包含完整的 IPC 桥接实现， 当 TCP 教程无法满足需求时，您可以研究这些实现。提供两种技术栈：

  • ROS 2：isaacsim.ros2.nodes、isaacsim.ros2.bridge 及相关 包。

  • UCX：isaacsim.ucx.nodes、isaacsim.ucx.core、 isaacsim.ucx.bridge。

每种技术栈都展示了完整桥接的布局方式：extension.toml 依赖项、原生插件、C++ 和 Python OmniGraph 节点以及传输后端。

在 Kit 文档的 OmniGraph 节点库中按名称搜索：OmniGraph。

Camera 和 Render Products#

将原始 RGB 像素传入自定义 IPC 节点，仅靠普通的 uchar[] OGN 输入是不够的。图像数据通常先经过 Replicator 流水线或 render product 链，然后才到达任何 IPC 编码器，而不是在图形编辑器中通过单根连线直接传输。关键步骤如下：

  1. 设置一个 render product（IsaacCreateRenderProduct 或 IsaacGetViewportRenderProduct）并附加一个 camera。

  2. 通过以下任一方式将 render product 接入回读机制：

    • Replicator 标注器（提供主机友好的 NumPy 数组）

    • Hydra 纹理链（通过 IsaacAttachHydraTexture 获取 GPU 句柄）

  3. 将生成的 CPU 可寻址字节或数组传入你的 IPC 编码器节点。

isaacsim.ros2.bridge 扩展的 camera 辅助节点是展示如何组装此流水线的具体参考示例。ROS 2 camera 发布者将 render product 连接到主机回读，再连接到 IPC。在构建自己的实现之前，浏览该源代码是理解此模式的最快方式。

在通过 compute 传递大型缓冲区之前，请参阅 Performance Considerations。Camera 帧是导致帧预算超支的常见原因。

测试你的 OmniGraph 节点实现#

用于 OmniGraph 节点的 Python 集成测试可以在运行时使用 og.Controller.edit 构建 Action Graph，以编程方式连接节点，驱动时间线，并对输出属性值进行断言。值得覆盖的领域包括：

  • 正确的输出：给定已知输入，节点产生预期的 db.outputs 值。

  • execOut 时序：节点仅在预期条件下触发 execOut。对于发送节点，这意味着每次评估都会触发。对于接收节点，这意味着仅在接收到数据时触发。

  • 重置行为：更改 URI 输入或停止时间线会关闭传输，随后的评估会干净地重新打开它。

  • 边缘情况：部分消息、对等方断开连接以及来自外部进程的格式错误数据。

对于 C++ 辅助函数（解析、编码和字节序），单元测试可以通过原生测试库（如 doctest）在 Isaac Sim 之外运行，这些库在 premake5.lua 中配置，并在 extension.toml 中引用。

将 [[test]] 条目指向你的测试模块，该条目位于你的 extension.toml 中。生成的测试驱动程序通常为 _build/<platform>/<config>/tests/tests-<your.extension.id>.sh。对于脚手架生成的扩展，测试位于 python/tests/ 中（模板已自动创建）。

有关上述模式（异步测试、OnImpulseEvent、空闲端口辅助函数和时间线控制）的示例，请参阅 source/extensions/isaacsim.examples.ipc/python/tests/。
