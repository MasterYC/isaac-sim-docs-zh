Stage 2：在 AGILE 中创建自定义人形机器人任务#

在此阶段，将 Stage 1 中的机器人定义连接到 AGILE 环境和 RSL-RL 训练运行器（AGILE 用于训练的强化学习库）。这种连接为 AGILE 提供了一个稳定的任务 ID，但尚未使 MDP 针对你的机器人变得正确。Stage 3 将检查并验证每个环境组件。

安装 AGILE#

AGILE 是一个用于通过强化学习开发人形机器人运动控制和移动操作行为的框架。它基于 Isaac Lab 的基于管理器的环境构建，并增加了人形机器人任务、训练和评估工作流、预训练策略以及部署工具。

请按照 Getting Started: Installation 开始使用 AGILE。

试用 AGILE#

在修改 AGILE 之前，运行一个已知的策略，以便在可视化器中预览预期结果。

uv run scripts/eval.py --task Velocity-G1-History-v0 \
    --checkpoint agile/data/policy/velocity_g1/unitree_g1_velocity_history_state_dict.pt \
    --viz kit

有关所有可用策略和支持的检查点格式，请参阅 Pre-trained Policies: Usage。

理解 AGILE 任务#

AGILE 任务是一系列配置选择。每一层都回答不同的问题：

robot configuration
        |
        |  Which USD, pose, joints, and actuators represent the robot?
        v
environment configuration
        |
        |  Which scene and MDP terms define the learning problem?
        v
Gymnasium task registration
        |
        |  Which stable task ID selects that environment?
        v
RSL-RL runner configuration
        |
        |  How does the learning algorithm collect and optimize experience?
        v
training run

将各层保持分离，可使多个任务复用同一机器人，也可使同一环境搭配不同的学习配置。请以 Task System: Directory Structure 作为文件布局参考。对于 H2，该链由以下部分实现：

agile/rl_env/
|-- assets/
|   `-- robots/
|       `-- unitree_h2.py
`-- tasks/
    `-- locomotion/
        `-- h2/
            |-- __init__.py
            |-- velocity_history_env_cfg.py
            `-- agents/
                `-- rsl_rl_ppo_cfg.py

机器人配置#

在 agile/rl_env/assets/robots/ 下创建机器人配置。阶段 1 已生成必要的源值；此步骤将这些值进行编码，以便每个环境都能生成相同的物理模型。

定义：

  • USD 路径和关节体生成属性。

  • 默认根位姿、关节位置和关节速度。

  • 腿部、腰部、手臂、头部和脚部的稳定关节名称组。

  • 脚部连杆以及接触时指示跌倒的连杆。

  • 执行器组、位置和速度限制、增益、电枢、摩擦、饱和力矩和延迟。

H2 文件首先为重要关节和连杆赋予稳定名称：

LEG_JOINT_NAMES = [".*_hip_.*_joint", ".*_knee_joint", ".*_ankle_.*_joint"]
WAIST_JOINT_NAMES = ["waist_yaw_joint", "waist_roll_joint", "waist_pitch_joint"]
ARM_JOINT_NAMES = [".*_shoulder_.*_joint", ".*_elbow_joint", ".*_wrist_.*_joint"]
HEAD_JOINT_NAMES = ["head_pitch_joint", "head_yaw_joint"]
FEET_LINK_NAMES = ["left_ankle_pitch_link", "right_ankle_pitch_link"]
DEFAULT_PELVIS_HEIGHT = 0.915

这些值将机器人定义与任务的其他部分关联起来。LEG_JOINT_NAMES 为受控集合贡献了 12 个腿部关节，阶段 3 通过添加 waist_roll_joint 和 waist_pitch_joint 将其完善，总共形成 14 个受控关节。FEET_LINK_NAMES 标识了基于接触的项所使用的刚体，而 DEFAULT_PELVIS_HEIGHT 为生成、奖励和终止提供了站立高度参考。根据阶段 1 的 USD 更新每个值，然后验证并记录关节表达式的解析顺序。

H2 随后按机械角色分离其电机。为了便于阅读，此摘录将执行器映射命名为 h2_actuators；AGILE 源代码将相同的映射直接放置在关节配置中。腿部组展示了将执行器模型连接到 MDP 的参数：

h2_actuators = {
    "legs": DelayedDCMotorCfg(
        ...,
        joint_names_expr=[
            ".*_hip_yaw_joint",
            ".*_hip_roll_joint",
            ".*_hip_pitch_joint",
            ".*_knee_joint",
        ],
        saturation_effort=360.0,
        min_delay=MIN_DELAY_PHY_STEPS,
        max_delay=MAX_DELAY_PHY_STEPS,
    ),
    "feet": DelayedDCMotorCfg(...),
    "waist": DelayedDCMotorCfg(...),
    "arms": DelayedDCMotorCfg(...),
    "head": DelayedDCMotorCfg(...),
}

joint_names_expr 将每个关节分配给一个执行器组。省略的 H2 字段提供每个关节的力矩和速度限制、刚度、阻尼以及电枢惯量。saturation_effort 限制了电机模型，而 min_delay 和 max_delay 将指令延迟随机化为零到四个物理步长。H2 使用单独的组，因为其脚部、腰部、手臂和头部具有不同的限制、增益和延迟行为。请将阶段 1 中测量的值带入相应的自定义组，而不是全局应用一个电机模型。

最后，关节配置结合了资产、初始状态和执行器组：

H2_DELAYED_DC_MOTOR = NestedRigidBodyArticulationCfg(
    spawn=sim_utils.UsdFileCfg(
        ...,
        usd_path=H2_USD_PATH,
        variants={"collision_profile": "feet_only", "hands": "none"},
        activate_contact_sensors=True,
    ),
    soft_joint_pos_limit_factor=0.9,
    init_state=ArticulationCfg.InitialStateCfg(
        pos=(0.0, 0.0, DEFAULT_PELVIS_HEIGHT + 0.1),
        joint_pos={
            ".*_hip_pitch_joint": -0.10,
            ".*_knee_joint": 0.30,
            ".*_ankle_pitch_joint": -0.20,
        },
        joint_vel={".*": 0.0},
    ),
    actuators=h2_actuators,
)

usd_path 选择资产。在参考 H2 路径中，它不是你准备的文件：fetch_h2_usd() 从 AGILE Robot Menagerie 检索 H2，正如 阶段 2 实际训练的内容 所解释的那样。当你替换为自己的人形机器人时，将 usd_path 指向你自己的 USD。H2 的 variants 选择请求仅包含脚部碰撞并省略手部，这些是 Menagerie 资产定义的变体集；你自己准备的 USD 将具有你编写的任何变体集，或者没有变体集。activate_contact_sensors 启用后续接触项使用的信号。soft_joint_pos_limit_factor=0.9 使训练限制保持在硬性 USD 限制之内，从而留出安全余量。

init_state 决定了生成位置和每个回合的重置姿态，并且会覆盖 USD 中编写的姿态。这里的值比 Stage 1 编写的 Unitree 发布的 home keyframe 蹲得更浅，因此请有意协调两者，而不是假设你的 USD 姿态会直接生效。无论你选择哪种方式，初始根节点高度和蹲姿必须在训练开始前产生一个无碰撞的姿态。

机器人配置描述了接收策略动作的仿真机器人。如果其初始姿态、执行器模型或限制与 USD 或后续部署运行时不一致，策略将针对错误的动力学进行训练。

环境配置#

完成下方的 Gymnasium 任务注册和 RSL-RL 运行器配置，然后使用 Stage 3 来配置并验证环境的 MDP 组件。

Gymnasium 任务注册#

创建任务目录并注册其 Gymnasium 环境。H2 任务使用此注册：

import gymnasium as gym

from . import agents

gym.register(
    id="Velocity-H2-History-v0",
    entry_point="isaaclab.envs:ManagerBasedRLEnv",
    disable_env_checker=True,
    kwargs={
        "env_cfg_entry_point": f"{__name__}.velocity_history_env_cfg:H2LowerVelocityHistoryEnvCfg",
        "rsl_rl_cfg_entry_point": f"{agents.__name__}.rsl_rl_ppo_cfg:H2VelocityHistoryPpoRunnerCfg",
    },
)

重要字段具有不同的职责：

  • id 是传递给 --task 的公共任务名称。它必须唯一且稳定，因为训练日志、评估命令和导出的包都使用它。

  • env_cfg_entry_point 选择环境配置类。对于 H2，它选择 H2LowerVelocityHistoryEnvCfg，该类组合了场景和所有 MDP 管理器。

  • rsl_rl_cfg_entry_point 选择 RSL-RL 运行器配置。它控制策略网络、 近端策略优化 (PPO) 算法、滚动长度、保存间隔、对称增强以及实验命名。

  • 父级 __init__.py 文件中的导入是有意为之的副作用。导入任务包会执行其 gym.register 调用，使得在脚本请求 Gymnasium 创建任务之前，任务 ID 就已可见。

请遵循 添加新任务 中的确切目录创建和父级导入流程。

RSL-RL 运行器配置#

H2 运行器以滚动、训练、检查点和输出设置开始：

@configclass
class H2VelocityPpoRunnerCfg(RslRlOnPolicyRunnerCfg):
    seed = 42
    num_steps_per_env = 24
    max_iterations = 50_000
    save_interval = 250
    experiment_name = "velocity_h2_lower"
    run_name = "velocity_h2_lower"
    empirical_normalization = False
    ...

num_steps_per_env=24 是每次 PPO 更新前从每个并行环境收集的滚动长度。max_iterations 限制运行时长，save_interval 控制原始检查点的保存频率。 experiment_name 选择日志目录；run_name 在其中标识此配置。为自定义人形机器人更改这两项，以免其输出与 H2 结果混淆。在首次比较时保持种子和归一化选择不变。

策略配置确定了将部署的 Actor 以及仅在训练期间使用的更大 Critic 的大小：

policy = RslRlPpoActorCriticCfg(
    init_noise_std=1.0,
    actor_hidden_dims=[256, 256, 128],
    critic_hidden_dims=[512, 256, 128],
    activation="elu",
)

H2 使用 256, 256, 128 Actor 和 512, 256, 128 Critic，因为 Critic 处理特权 观测值。init_noise_std 控制初始探索，activation 选择非线性激活函数。 在首次基线测试中保留此网络；仅在环境学会且测得的容量或优化问题促使更改时才进行修改。

PPO 块定义了更新行为和 H2 特定的对称增强：

algorithm = RslRlPpoAlgorithmCfg(
    ...,
    clip_param=0.2,
    learning_rate=1.0e-3,
    gamma=0.99,
    lam=0.95,
    desired_kl=0.01,
    symmetry_cfg=RslRlSymmetryCfg(
        use_data_augmentation=True,
        use_mirror_loss=False,
        data_augmentation_func=lr_mirror_H2,
    ),
)

clip_param 限制每次策略更新，learning_rate 控制其步长，gamma 和 lam 设置回报和优势函数的时间范围。desired_kl 是完整 H2 配置中自适应调度使用的目标值。对称函数是最可能需要立即替换的参数： lr_mirror_H2 假设了 H2 的观测和动作顺序，因此在验证自定义镜像映射之前，它对于自定义顺序无效。

历史任务继承这些设置并更改其输出标识：

@configclass
class H2VelocityHistoryPpoRunnerCfg(H2VelocityPpoRunnerCfg):
    experiment_name = "velocity_h2_history"
    run_name = "velocity_h2_history"
    wandb_project = "Velocity-H2-History"

在创建 自定义运行器时，请在 agile/rl_env/tasks/locomotion/h2/agents/rsl_rl_ppo_cfg.py 中使用完整的 H2 类。上面的摘录仅显示您可能需要更改的参数；其余参数应保持 H2 基线值。 算法：PPO 部分解释了 AGILE 集成的算法，而阶段 4 涵盖了训练期间的诊断。
